# SQLite v01 guarantee and failure-test ledger

This is a test plan for the published [SQLite v01 contract](sqlite-v01.md), not a new API contract. “Next caller” means a separate, subsequent scope on the same `Database`, preferably with one reader when testing reader reuse. A scenario is a proposed conformance case until its linked issue is implemented. Source references distinguish public promises from the current Linux provider in `archaic-java/ffm-sqlite`; provider behavior alone does not create a portable guarantee.

| Guarantee and public source | Catalog case / failure scenario | Expected state for the next caller | Placement |
| --- | --- | --- | --- |
| Write commits on normal return; failure rolls back and propagates the original checked or unchecked throwable. `Database.write`, `Work`, [SQLite v01](sqlite-v01.md). | `transaction-commit-and-rollback`: insert, throw a specific checked or unchecked instance; test a SQL constraint failure. Existing `SqliteProviderContract` covers basic rollback and checked identity. [#8](https://github.com/archaic-java/service-catalog/issues/8). | No partial rows from failed work; next write and read succeed. A cleanup failure is suppressed on the original failure when cleanup can run. | Catalog behavior; provider fault tests for rollback failures. |
| Reads use a read-only connection; in WAL, an established read transaction sees a stable snapshot while a writer commits. `Database.read`, [SQLite v01](sqlite-v01.md). | `read-snapshot`: establish a snapshot by stepping a query, commit from a second scope, read again in the same scope; attempt a write in a read scope. Existing check covers rejection and concurrent uncommitted visibility, but not a stable snapshot. [#8](https://github.com/archaic-java/service-catalog/issues/8). | The old reader keeps its snapshot; a fresh read sees the commit. After rejected SQL, the next read succeeds. | Catalog. |
| One writer and a fixed number of readers; `wait` bounds **lease acquisition**, not SQL execution. `Sqlite.open`, [SQLite v01](sqlite-v01.md). | `lease-admission`: exhaust a one-reader pool and the writer separately; expect a bounded acquisition failure, release, then reacquire. [#9](https://github.com/archaic-java/service-catalog/issues/9). | No lost lease; next caller enters and can query or write. Timing allows scheduling margin; no execution-time promise. | Catalog; platform-specific scheduling details in provider tests. |
| An interrupted lease wait fails without consuming a lease and leaves the thread interrupted. [SQLite v01](sqlite-v01.md) promises bounded acquisition; interrupt outcome is **observed provider behavior**, not yet specified by v01. | `interrupted-lease-wait`: block on the only reader/writer, interrupt waiting thread, release holder. [#9](https://github.com/archaic-java/service-catalog/issues/9). | In the current provider, the waiting thread gets `SqliteException` with an `InterruptedException` cause and restored interrupt flag; a later scope succeeds. Do not demand this exact outcome across providers until policy is decided. | Provider-specific until standardized. |
| Session and statements expire with scope; outstanding statements are closed. Native TEXT and BLOB results are copied into Java values. `Session`, `Statement`, [SQLite v01](sqlite-v01.md). | `scoped-lifetime-and-owned-values`: retain handles past return/failure, keep fetched values past scope and mutate a bound input byte array. Existing contract checks value round trips, not expiry. [#10](https://github.com/archaic-java/service-catalog/issues/10). | Expired handles cannot access the returned connection; copied values remain readable and independent; next scope can prepare and step. Exact exception type for expired handles is not specified. | Catalog; native lifetime and memory checks in provider tests. |
| `Session.cancel()` may be called from another thread during a live scope and asks SQLite to interrupt running SQL; it may be too late to affect completed SQL. [SQLite v01](sqlite-v01.md). | `cancel-and-reuse`: coordinate a running statement and cancellation, wait for both threads to finish; distinguish an actual `SQLITE_INTERRUPT` from a race after completion. Existing contract checks one long read cancellation. [#9](https://github.com/archaic-java/service-catalog/issues/9). | When the query was interrupted, subsequent work on the sole connection succeeds; a failed write has no partial rows. Caller keeps scope live through `cancel()`. | Catalog deterministic cancellation; provider-specific timing/hazard harness. |
| Backup publishes a consistent complete image to a **new** path with an atomic hard link; never replaces an existing target. `Database.backup`, [SQLite v01](sqlite-v01.md). | `backup-publication`: reopen image, reject existing destination, force backup failure/timeout and inspect target and temporary files. Existing contract checks committed snapshot during a write and refusal to replace. [ffm-sqlite#4](https://github.com/archaic-java/ffm-sqlite/issues/4). | Existing target unchanged; failed backup has no published target, and subsequent backup/read succeeds after the cause is removed. Temporary cleanup errors are preserved as suppressed failures where possible. | Catalog for publication and replacement; provider harness for I/O, timeout and cleanup faults. |
| Passive checkpoint reports WAL frames; active reader can keep it incomplete; it does not wait for readers. `Database.checkpoint`, `Checkpoint`, [SQLite v01](sqlite-v01.md). | `passive-checkpoint`: hold an old read snapshot over a commit; compare progress while held and after release. Existing contract checks nonnegative and ordered frame counts only. [ffm-sqlite#4](https://github.com/archaic-java/ffm-sqlite/issues/4). | A subsequent checkpoint and read still work; do not require exact frame counts across SQLite versions. | Catalog for observable progress, provider tests for contention and errors. |
| Close follows finished scopes; closing during an active operation fails instead of freeing native pointers. `Database.close`, [SQLite v01](sqlite-v01.md). | `close-with-active-scope`: attempt close while holding a scope, then finish it; close again. `close-after-failure`: check no active native handles after failures. [#10](https://github.com/archaic-java/service-catalog/issues/10). | After rejected close, existing scope completes and a new scope works; successful close rejects future scopes. Reuse after a native close failure is **undecided**. | Catalog for active/successful close; provider harness for native close failure. |

## Decisions still required

| Question | Current public contract and provider observation | Decision needed before a portable test |
| --- | --- | --- |
| Nested scopes | v01 makes no nesting promise. The provider has a finite read queue and a non-reentrant acquisition path for writers; nested calls can time out or acquire a different reader. | Forbid explicitly, define nesting, or leave unspecified; do not assume nested write transactions. |
| Cross-thread session use beyond `cancel()` | The contract permits only `cancel()` from another thread; provider methods otherwise have no ownership guard. | Decide whether misuse must fail predictably or is outside the contract. |
| Manual transaction-control SQL | `Session.prepare` accepts SQL without a transaction-control filter; the coordinator executes `BEGIN` and `COMMIT`/`ROLLBACK`. | Define whether user `BEGIN`, `COMMIT`, `ROLLBACK`, or savepoints are prohibited, supported, or unspecified. |
| Configuration PRAGMAs | Provider establishes WAL and foreign keys but `prepare` does not filter PRAGMAs; a caller may alter connection state. | Define allowable PRAGMAs and responsibility for restoring connection settings. |
| Rollback failure | Provider preserves the original throwable and suppresses rollback failure, then returns the connection to the pool without a health check. | Decide whether to discard/reopen a connection, close the database, or otherwise prevent unsafe reuse. No clean-reuse guarantee is asserted for this condition. |
| Durability and synchronous mode | v01 promises transaction semantics and a published backup, but no power-loss guarantee or `synchronous` setting. Provider enables WAL without setting `PRAGMA synchronous`. | Choose a durability level and platform assumptions before claiming crash/power-loss persistence. A process-kill campaign alone cannot prove power-loss durability. |

## Implemented transaction case identifiers

`TransferRollback(failAfter=1|2|3)` checks rollback after each statement, exception identity and next-writer reuse; `TransactionConstraints` checks immediate `CHECK` failure and deferred foreign-key failure at COMMIT; `StableSnapshot` checks an established reader across a concurrent commit; `ReadOnlyReuse` checks rejection followed by a clean read and transfer. These cases are proposed in [the transaction test PR](https://github.com/archaic-java/service-catalog/pull/13), based on the Minau case split.

## Execution and evidence

Implement in this order: [split cases](https://github.com/archaic-java/service-catalog/issues/7) → [wire provider Minau v02](https://github.com/archaic-java/ffm-sqlite/issues/2) → deterministic transaction, lifetime, lease, lock and backup cases → seeded model and child-process crash campaigns. Catalog cases exercise observable v01 behavior across providers; Linux SQLite lock, native fault, file publication and process supervision machinery stays with `ffm-sqlite`. Preserve original failures and attach cleanup failures as suppressed; any observed provider bug gets a retained regression and a focused provider correction. Pin catalog and Minau revisions when verifying a provider PR.
